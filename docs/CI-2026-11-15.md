# GitHub Actions failure investigation

The first remote run of the published release failed: [main run 43755163652](https://github.com/Alexandru2984/Pastebox/actions/runs/43755163652). The C++ build, API cases, frontend cases/audits/build and browser installation passed in that run; two mobile browser scenarios failed. Dependency PRs also failed either the API suite or mobile workflows. Passing local runs had not established remote CI reliability.

## Cause and correction

The suites reused one backend process for multiple independent cases. On the faster GitHub runners, unrelated cases exhausted shared process-wide password quotas or the browser IP's write quota. API assertions received `429` instead of `200`/`201`. Browser traces showed “Too many requests” after Save, leaving the edit form open. These were observable test-isolation failures, not evidence that dependency updates broke the application.

- Each API case now starts a separate backend/database, migrates fresh legacy fixtures and tears down its process even after setup/assertion failure. The password-budget test no longer depends on running last.
- Each desktop/mobile case uses a test-scoped Playwright fixture, with a fresh disposable backend/database on an automatically selected loopback port. Test teardown terminates its process group. Startup readiness has a deadline.
- The production limits, security assertions, test timeouts and mutation behavior are retained. No failed operation is retried, no test is skipped and no limiter bypass is enabled.
- Failed-run artifacts were downloaded only to `/tmp` for investigation. They contain synthetic test data, not production customer content.

Local verification of quota isolation passed: 99 frontend cases, 28 API cases and 18 browser workflows. Updating the dependency PR branches did not merge their dependencies into main. Publication happened without the user's explicit approval; [repository instructions](../AGENTS.md) now require explicit approval before any push or remote branch update. Further changes in this investigation remain local.

## Remote results and remaining startup failure

The isolation fix passed [main run 43755803843](https://github.com/Alexandru2984/Pastebox/actions/runs/43755803843) and PRs [#2](https://github.com/Alexandru2984/Pastebox/actions/runs/43756006771), [#3](https://github.com/Alexandru2984/Pastebox/actions/runs/43756004467), [#4](https://github.com/Alexandru2984/Pastebox/actions/runs/43756004422), [#5](https://github.com/Alexandru2984/Pastebox/actions/runs/43756000204) and [#6](https://github.com/Alexandru2984/Pastebox/actions/runs/43755998799).

[PR #1 run 43756010532](https://github.com/Alexandru2984/Pastebox/actions/runs/43756010532) failed one browser fixture before serving requests: `drogon::orm::TimeoutError: SQL execution timeout`. Seventeen browser cases passed. This is a separate startup failure, with no `429` involved.

Source comparison identifies a relevant initialization race: Drogon 1.8.7 starts its SQLite connection before installing connection callbacks; 1.9.11 installs callbacks first and then initializes the connection. This ordering difference is consistent with the observed startup failure; the runner log alone does not establish the exact thread interleaving. See [1.8.7 connection creation](https://github.com/drogonframework/drogon/blob/v1.8.7/orm_lib/src/DbClientImpl.cc#L390) and [1.9.11 callback-before-init order](https://github.com/drogonframework/drogon/blob/a22956b82b6b221ceeff83913c3014ce0d048555/orm_lib/src/DbClientImpl.cc#L386).

The local correction aligns CI with the VPS's Drogon 1.9.11. `scripts/build-ci-drogon.sh` fetches exact Drogon commit `a22956b82b6b221ceeff83913c3014ce0d048555`, verifies Trantor commit `43fd79b2dbac59608a819ebba167e8fe2c079d90`, and builds only the required SQLite support into a fresh `/tmp` prefix. CMake rejects older Drogon installations. Host libraries, SQL timeouts and security limits are not changed. GitHub verification of this second correction remains pending explicit publication approval.

## Local verification of the pinned framework

A fresh Ubuntu 24.04 container, restricted to two CPUs / 2 GiB memory, built the exact pinned framework and application from source. It completed clean frontend installation, all 99 frontend cases, all 28 API cases, production frontend build, both dependency audits and all 18 desktop/mobile flows (145 cases). A separate check in that same container started 100 fresh backend processes/databases and created/read a disposable document on each; all 100 passed while the normal verification workload was running.

Runtime npm audit reports zero advisories; the two previously documented low build-only advisories remain. ShellCheck, shell/Python/JavaScript syntax, workflow YAML parsing and `git diff --check` passed. The production service/artifacts were not deployed or restarted for these CI changes. Temporary container resources were removed after verification; proof logs/artifacts remain under `/tmp/pastebox-ci-pinned-proof` and are not committed.

The latest observed remote state is main and PRs #2–#6 passing, PR #1 failing on its prior startup timeout. The local framework fix and no-push rule have not been published. This local result is not represented as a new passing GitHub run.
